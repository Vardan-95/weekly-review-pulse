# Edge Cases — Phase 2: Ingestion & Safety

Companion to: [ImplementationPlan.md § Phase 2](../ImplementationPlan.md#phase-2--ingestion--safety)

| # | Scenario | Expected handling |
|---|---|---|
| 1 | Play Store scraper hits a block/rate-limit/CAPTCHA wall | Detected distinctly from a generic network error, retried with backoff, and if still blocked, the run fails clearly rather than silently returning zero reviews as if that were a real result |
| 2 | App Store RSS pagination boundary — reviews exactly at the window edge, or multiple reviews with identical timestamps at that edge | Window filter is inclusive/exclusive consistently (define and document the boundary rule); ties don't cause duplicate or dropped reviews |
| 3 | Rating-only review with no text body | Ingested with `body = ""`/`null`, not dropped outright (rating still has signal) but excluded from clustering/quote-eligibility since there's no text |
| 4 | Non-English review text (e.g. Hindi in Devanagari script) | Ingested (ingestion itself doesn't filter), but dropped in the Scrub stage by the language filter before it reaches storage or clustering — see #11-#15 below for the filter's own edge cases |
| 5 | A review is edited by its author after being ingested in a prior week's run | Treated as a new/updated record for `(source, review_id)` in the current window rather than silently ignored as "already seen" — the review store is not a permanent global dedup cache across weeks, only within a single run's window |
| 6 | Extremely long review text (a multi-paragraph essay) | Scrubber and downstream stages handle it without truncation errors; a length cap may be applied but must be explicit and logged, not a silent cutoff |
| 7 | PII scrubber over-redaction: legitimate text pattern-matches as PII (e.g. "10/10", a version number like "v2.4.1", an in-app numeric code the user quotes) | Precision target from the evaluation file bounds this; false positives should degrade quote readability, not corrupt theme-level meaning |
| 8 | Injection attempt using unicode tricks/homoglyphs or zero-width characters to evade regex-based detection | Documented as a known residual risk; flag on normalized/NFKC text where feasible, but this phase does not guarantee 100% adversarial robustness — only that clean-text injection attempts are caught |
| 9 | Zero reviews returned for a product/window (new product, extremely quiet week) | Ingestion completes successfully with an empty set; this is a valid state the pipeline must propagate cleanly, not an error |
| 10 | Same review appears from both sources with near-identical text (e.g. a user cross-posted) | Not deduplicated across sources — `(source, review_id)` keys are source-scoped by design; documented as expected behavior, not a bug |
| 11 | Review is pure emoji, no words at all | After emoji stripping the text is empty; treated as language-neutral (nothing to judge) and kept, consistent with how rating-only reviews are handled — not rejected just for having no words |
| 12 | Review mixes an English sentence with a small amount of Devanagari (e.g. one Hindi word/phrase quoted inside otherwise-English text) | The non-Latin-script ratio may stay below the rejection threshold if the Hindi portion is small relative to total letters, so the review is kept with the Hindi fragment left in place; documented as a known partial-miss — the filter favors precision (not wrongly rejecting real English feedback) over catching every mixed-language case |
| 13 | Hinglish density sits right at the classification threshold | Threshold-based scoring means a review right at the boundary could go either way depending on exact word choice; documented as an approximate heuristic, not an exact rule |
| 14 | An English review happens to contain a word that coincidentally matches the Hinglish wordlist (e.g. a name or loanword) | The density threshold requires enough matching words relative to total word count, not just one match, which limits false positives from a single coincidental hit |
| 15 | Multi-codepoint emoji sequences (skin-tone modifiers, ZWJ-joined family/profession emojis) | Covered explicitly by the emoji regex's skin-tone-modifier and zero-width-joiner ranges; emoji sequences using code points outside the covered ranges may leave stray characters behind — documented as a residual risk, not exhaustively tested against every Unicode emoji release |
